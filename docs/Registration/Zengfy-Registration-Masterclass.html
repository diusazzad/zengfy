১. নির্বাহী সারসংক্ষেপ (Executive Summary)

একটি ডিজিটাল প্ল্যাটফর্ম বা ইকোসিস্টেমের প্রথম এবং প্রধান প্রবেশদ্বার হলো রেজিস্ট্রেশন এবং আইডেন্টিটি সিস্টেম (Registration & Identity System)। অধিকাংশ প্রজেক্টে রেজিস্ট্রেশনকে শুধুমাত্র একটি সাধারণ ওয়েব ফর্ম ও ডেটাবেজ ইনসার্ট অপারেশন হিসেবে ভাবা হয়। কিন্তু বাস্তব প্রডাকশন পরিবেশে এটি সিকিউরিটি, ক্রিপ্টোগ্রাফি, সিস্টেম রেজিলিয়েন্স, আইনি কমপ্লায়েন্স এবং ইউজার এক্সপেরিয়েন্সের এক জটিল সমন্বয়।

Zengfy ইকোসিস্টেমের জন্য আমাদের কৌশলগত সিদ্ধান্ত:

  1. Day 0 (প্রথম দিন): অতি-সহজ ও ঘর্ষণহীন (Frictionless) রেজিস্ট্রেশন। ইউজার কেবল ৩টি ফিল্ড পূরণ করবেন:
    • পুরো নাম (Full Name)
    • ইমেইল ঠিকানা (Email Address)
    • পাসওয়ার্ড (Password)
      (অথবা Google 1-Tap Sign-In এর মাধ্যমে ০-ফিল্ডে তাৎক্ষণিক একাউন্ট খোলা)।
  2. জিরো-কস্ট ভেরিফিকেশন (Zero-Dollar Verification): প্রাথমিক পর্যায়ে ব্যয়বহুল SMS OTP সম্পূর্ণ পরিহার করে নিরাপদ ক্রিপ্টোগ্রাফিক ইমেইল ভেরিফিকেশন লিংক চালু রাখা।
  3. প্রগ্রেসিভ প্রোফাইলিং ও ব্যাজ সিস্টেম (Progressive Profiling & Badges): ফোন নাম্বার, জাতীয় পরিচয়পত্র (NID) বা উন্নত নাগরিক ভেরিফিকেশন পরবর্তী সময়ে একাউন্ট সেন্টারে (Account Center) ব্যাজ বা ট্রাস্ট টিয়ার (Trust Tier) আকারে যুক্ত হবে।

১. আইডেন্টিটি, প্রমাণীকরণ ও অনুমোদন (The Holy Trinity of Auth)

সফটওয়্যার ইঞ্জিনিয়ারিংয়ে প্রায়ই তিনটি ধারণাকে গুলিয়ে ফেলা হয়:

[ ইউজার আইডেন্টিটি (Identity) ]  ---> "আপনি কে?" (নাম, ইমেইল, হ্যান্ডেল)
              │
              ▼
[ প্রমাণীকরণ (Authentication) ]  ---> "আপনি কি আসলেই সেই ব্যক্তি?" (পাসওয়ার্ড, ওটিপি, পাসকি)
              │
              ▼
[ অনুমোদন (Authorization) ]     ---> "আপনার কি এই সিস্টেমে প্রবেশের অধিকার আছে?" (রোল, পারমিশন)
  1. আইডেন্টিটি (Identity): সিস্টেমে ইউজারের একক অস্তিত্ব। এটি একটি অনন্য আইডেন্টিফায়ার (যেমন: sazzad@zengfy.com বা UUID)।
  2. অথেনটিকেশন বা প্রমাণীকরণ (Authentication - AuthN): প্রেরিত আইডেন্টিটি সত্য কি না তা যাচাই করার প্রক্রিয়া (যেমন: সঠিক পাসওয়ার্ড প্রদান করা)।
  3. অথরাইজেশন বা অনুমোদন (Authorization - AuthZ): যাচাইকৃত আইডেন্টিটিকে কোন কোন কাজ করার অনুমতি দেওয়া হয়েছে তা নির্ধারণ করা (যেমন: ইউজার কি সাধারণ নাগরিক, নাকি অ্যাডমিন?)।

২. ডে ০ ফিলোসফি: ৩টি ফিল্ড কেন? (The Day 0 Three-Field Philosophy)

২.১ কনভার্সন ড্রপ-অফ ম্যাথ (Conversion Drop-off Law)

ই-কমার্স ও সাস (SaaS) ইন্ডাস্ট্রির বহুল পরিচিত গবেষণা অনুযায়ী:

  • ফোন নাম্বারে বাধ্যতামূলক SMS OTP যুক্ত করলে নেটওয়ার্ক ডিলে এবং ইউজারের দ্বিধার কারণে সাইন-আপ ড্রপ-অফ আরও ২৫% থেকে ৩৫% বৃদ্ধি পায়।

২.২ ডে ০ রেজিস্ট্রেশনের গোল্ডেন ফিল্ড ত্রয়ী

Zengfy প্ল্যাটফর্মে প্রথম দিনে আমরা শুধু তিনটি মৌলিক ফিল্ড নিচ্ছি:

  2. Email Address (ইমেইল ঠিকানা): গ্লোবাল ইউনিক আইডেন্টিফায়ার, পাসওয়ার্ড রিকভারি চ্যানেল এবং ফ্রিতে ভেরিফিকেশন পাঠানোর মাধ্যম।
  3. Password (পাসওয়ার্ড): প্রাথমিক প্রমাণীকরণ মেকানিজম (কমপক্ষে ৮ অক্ষর, মিশ্র ক্যারেক্টার)।

লক্ষ্য: পাসওয়ার্ড হ্যাশিংয়ের আধুনিক স্ট্যান্ডার্ড (Argon2id বনাম Bcrypt), টাইমিং অ্যাটাক প্রিভেনশন, সল্ট ও সিক্রেট পেপার এবং রেট লিমিটিং মেকানিজম বাস্তবায়ন করা।

১. পাসওয়ার্ড হ্যাশিং অ্যালগরিদম: কেন Argon2id সেরা?

অনেক ডেভেলপার এখনও MD5, SHA-1 বা সাধারণ SHA-256 দিয়ে পাসওয়ার্ড হ্যাশ করার মতো মারাত্মক ভুল করেন। SHA ফ্যামিলি ডিজাইন করা হয়েছিল ডেটা ইন্টিগ্রিটি ও অতি দ্রুত হ্যাশ গণনার জন্য। আধুনিক GPU প্রতি সেকেন্ডে কোটি কোটি SHA-256 হ্যাশ ব্রুট-ফোর্স করতে পারে!

অ্যালগরিদম মেমোরি হার্ডনেস GPU/ASIC রেজিস্ট্যান্স সাইড-চ্যানেল সুরক্ষা প্রডাকশন সুপারিশ
MD5 / SHA-256 একদম নেই ০% (অত্যন্ত দুর্বল) নেই ❌ সম্পূর্ণ নিষিদ্ধ
Bcrypt খুব কম (৪ KB) মাঝারি (CPU-bound) ভালো ⚠️ গ্রহণযোগ্য (তবে ৭২ বাইট লিমিট আছে)
Argon2id সর্বোচ্চ (কনফিগারযোগ্য) সর্বোচ্চ (Memory-hard) সর্বোচ্চ (Hybrid resistance) ✅ স্বর্ণমান (Gold Standard)

Argon2id প্যারামিটার কনফিগারেশন (OWASP সুপারিশকৃত):

  • Memory Cost ($m$): 65536 KiB (64 MB)
  • Time Cost ($t$): 3 Iterations
  • Parallelism ($p$): 4 Threads
// Node.js এ argon2id হ্যাশিংয়ের প্রডাকশন এক্সাম্পল
import argon2 from 'argon2';

export async function hashPassword(plainPassword) {
    return await argon2.hash(plainPassword, {
        type: argon2.argon2id,
        memoryCost: 65536, // 64 MB
        timeCost: 3,
        parallelism: 4
    });
}

export async function verifyPassword(hash, plainPassword) {
    return await argon2.verify(hash, plainPassword);
}

২. ক্রিপ্টোগ্রাফিক সল্ট (Salt) এবং সার্ভার পেপার (Pepper)

  1. সল্ট (Salt): প্রতিটি ইউজারের জন্য স্বয়ংক্রিয়ভাবে তৈরি হওয়া অনন্য র‍্যান্ডম বাইটস (Argon2id ও Bcrypt স্বয়ংক্রিয়ভাবে হ্যাশের ভেতর সল্ট সংরক্ষণ করে)। এটি রেইনবো টেবিল অ্যাটাক সম্পূর্ণ ধ্বংস করে।
  2. সার্ভার পেপার (Pepper): একটি গোপন মাস্টার কি (Secret Key) যা ডেটাবেজে কখনোই থাকে না। এটি অ্যাপ্লিকেশনের এনভায়রনমেন্ট ভেরিয়েবলে (APP_PEPPER) অথবা ক্লাউড HSM/KMS-এ সংরক্ষিত থাকে।
    • পাসওয়ার্ড হ্যাশ করার আগে পেপার দিয়ে HMAC তৈরি করা হয়: $$ ext{Pre-Hash} = ext{HMAC-SHA256}( ext{Password}, ext{APP_PEPPER})$$
    • এরপর প্রি-হ্যাশকে Argon2id দিয়ে হ্যাশ করা হয়।
    • ফলাফল: হ্যাকার যদি ডেটাবেজ ডাম্প সম্পূর্ণ চুরিও করে নেয়, সার্ভার পেপার ছাড়া একটি পাসওয়ার্ডও ক্র্যাক করতে পারবে না।

৩. টাইমিং অ্যাটাক প্রিভেনশন (Timing-Safe Comparison)

সাধারণ স্ট্রিং কম্প্যারিজন (string1 === string2) প্রথম অমিল পাওয়ার সাথে সাথেই এক্সিকিউশন বন্ধ করে দেয়। হ্যাকাররা মাইক্রোসেকেন্ড নিখুঁতভাবে পরিমাপ করে টোকেন অনুমান করতে পারে (Side-Channel Timing Attack)।

ক্রিপ্টোগ্রাফিক টোকেন ও সিগনেচার মেলানোর সময় সর্বদা কনস্ট্যান্ট-টাইম কম্প্যারিজন ব্যবহার করতে হবে:

import crypto from 'crypto';

// ক্ষতিকর পদ্ধতি:
// if (userProvidedToken === dbToken) { ... } // ❌ টাইমিং অ্যাটাকে আক্রান্ত হতে পারে!

// নিরাপদ পদ্ধতি:
const isMatch = crypto.timingSafeEqual(
    Buffer.from(userProvidedHash, 'hex'),
    Buffer.from(storedHash, 'hex')
); // ✅ সর্বদা সমান সময় নেয়

বোট ও হ্যাকাররা বটনেট দিয়ে হাজার হাজার ভুয়া একাউন্ট তৈরি করে সিস্টেম ক্র্যাশ করাতে পারে। Redis-ভিত্তিক Sliding Window Counter অ্যালগরিদম দিয়ে আমরা রেজিস্ট্রেশন সুরক্ষিত রাখব:

২. ইমেইল ডেলিভারেবিলিটি ট্রায়াঙ্গেল (SPF, DKIM, DMARC)

ইমেইল যাতে ইউজারের স্প্যাম ফোল্ডারে না গিয়ে সরাসরি ইনবক্সে পৌঁছায়, সেজন্য তিনটি DNS রেকর্ড সঠিকভাবে কনফিগার করতে হয়:

          [ ডোমেন ও ডিএনএস (DNS) ]
            ╱        │        ╲
           ╱         │         ╲
   [ SPF রেকর্ড ] [ DKIM কি ] [ DMARC পলিসি ]
   "কোন সার্ভার     "ক্রিপ্টো        "মেইল না মিললে
    মেইল পাঠাবে"     ডিজিটাল সাইন"    কী ব্যবস্থা নেবে"
  1. SPF (Sender Policy Framework): ডিএনএস টিএক্সটি (TXT) রেকর্ড যা বিশ্বকে জানায় কোন কোন আইপি এড্রেস আপনার ডোমেইন থেকে বৈধভাবে মেইল পাঠাতে পারে।
    উদাহরণ: v=spf1 ip4:185.120.45.10 include:_spf.zengfy.com ~all
  2. DKIM (DomainKeys Identified Mail): প্রতিটি পাঠানো ইমেইলের হেডারে প্রাইভেট কি দিয়ে ক্রিপ্টোগ্রাফিক সাইন থাকে। প্রাপক মেইল সার্ভার পাবলিক কি দিয়ে যাচাই করে যে পথিমধ্যে মেইলটি কেউ বদল করেছে কি না।
  3. DMARC (Domain-based Message Authentication, Reporting, and Conformance): রিসিভারকে নির্দেশ দেয় যদি SPF বা DKIM ফেইল করে, তবে মেইলটি রিজেক্ট বা কোয়ারেন্টাইন করতে হবে।

৩. স্টেটলেস ক্রিপ্টোগ্রাফিক ভেরিফিকেশন লিংক আর্কিটেকচার

ইউজারকে পাঠানো ভেরিফিকেশন লিংকের আর্কিটেকচার অত্যন্ত গুরুত্বপূর্ণ:

https://zengfy.top/verify-email?id=UUID&expires=1792323553&signature=HMAC_SHA256

কেন প্লেইনটেক্সট টোকেন ডেটাবেজে রাখা নিষেধ?

অনেক ডেভেলপার ডেটাবেজে verify_token কলামে প্লেইনটেক্সট স্ট্রিং রেখে দেন। কোনো দুর্বলতার কারণে ডেটাবেজ লিক হলে আক্রমণকারী সকলের টোকেন পেয়ে ভুয়া ভেরিফিকেশন করে ফেলতে পারে।

সঠিক ডিজাইন:

  1. ইউজারের জন্য একটি ক্রিপ্টোগ্রাফিক হাই-এনট্রপি র‍্যান্ডম টোকেন তৈরি করুন:
    const rawToken = crypto.randomBytes(32).toString('hex'); // ৬৪ অক্ষরের নিরাপদ টোকেন
  2. ডেটাবেজে শুধুমাত্র এর SHA-256 হ্যাশ সংরক্ষণ করুন:
    const tokenHash = crypto.createHash('sha256').update(rawToken).digest('hex');
// DB-তে tokenHash সেভ হবে, rawToken কখনোই DB-তে যাবে না!
  3. ইউজারকে লিংকে rawToken পাঠানো হবে। যখন ইউজার ক্লিক করবেন, ব্যাকএন্ড আবার সেটিকে SHA-256 হ্যাশ করে ডেটাবেজের সাথে মিলাবে।
  4. টোকেনের মেয়াদ থাকবে সর্বোচ্চ ২৪ ঘণ্টা এবং একবার ভেরিফাই হলে টোকেনটি সাথে সাথে এক্সপায়ার (consumed_at = NOW()) হয়ে যাবে।

১. কনকারেন্সি এবং রেস কন্ডিশন (Double Submit Race Condition)

ধরা যাক, একজন ইউজার রেজিস্ট্রেশন ফর্মে সাবমিট বাটনে দ্রুত দুইবার ক্লিক করলেন (Double-click)।

  1. ফ্রন্টএন্ড স্তরে: বাটনে ক্লিক করার সাথে সাথে বাটন disabled করা এবং লোডিং স্পিনার দেখানো।

২. ইউনিকোড ও আন্তর্জাতিকীকরণ সমস্যা (Unicode Homograph Attacks)

আক্রমণকারীরা একই দেখতে কিন্তু ভিন্ন ক্যারেক্টার দিয়ে ক্ষতিকর ডোমেইন বা ইমেইল স্পুফ করতে পারে।

  • ল্যাটিন ইংরেজি অক্ষর a (ASCII 0x61)
  • সিরিলিক রাশিয়ান অক্ষর а (Unicode U+0430)

উভয় অক্ষর দেখতে হুবহু একই রকম (a), কিন্তু কম্পিউটারের জন্য দুটি সম্পূর্ণ ভিন্ন ক্যারেক্টার!

const cleanEmail = rawEmail.trim().toLowerCase().normalize('NFKC');

৩. প্লাস-ট্যাগিং ও ডট-ইনসেনসিটিভিটি (Plus-Addressing & Dot-Tricks)

গুগল জিমেইল অ্যাকাউন্টে একটি বিশেষ সুবিধা আছে:

  • s.a.z.z.a.d.zengfy@gmail.com
  • sazzad.zengfy+freecredit@gmail.com

গুগলের কাছে এই তিনটি ঠিকানাই এক। কিন্তু সাধারণ ব্যাকএন্ড এদের তিনটি ভিন্ন ইমেইল হিসেবে গণ্য করে। এর ফলে অসাধু ইউজাররা ট্রায়াল ক্রেডিট বা ফ্রি কুপন অপব্যবহার করার জন্য শত শত একাউন্ট খুলে ফেলে।

সমাধান:

রেজিস্ট্রেশনের সময় একটি ক্যানোনিক্যাল ইমেইল (Canonical Email) প্রসেসিং ফাংশন ব্যবহার করা:

export function canonicalizeEmail(email) {
    let [localPart, domain] = email.trim().toLowerCase().split('@');
    if (domain === 'gmail.com' || domain === 'googlemail.com') {
        localPart = localPart.replace(/\./g, ''); // সব ডট মুছে ফেলা
        localPart = localPart.split('+')[0];      // প্লাস এবং তার পরের সব অক্ষর বাদ দেওয়া
    }
    return `${localPart}@${domain}`;
}

const DISPOSABLE_DOMAINS = new Set([
    'tempmail.com', '10minutemail.com', 'mailinator.com',

export function isDisposableEmail(domain) {
    return DISPOSABLE_DOMAINS.has(domain.toLowerCase());
}

import argon2 from 'argon2';
import crypto from 'crypto';
import { db } from '../config/database';

export class AuthService {
  /**
   * ডে ০ মিনিমালিস্ট রেজিস্ট্রেশন প্রসেস
   */
  async registerUser(data: { fullName: string; email: string; password: string }) {
    return await db.transaction(async (trx) => {
      // ১. ইমেইল পূর্বে ব্যবহৃত হয়েছে কি না চেক
      const existing = await trx('users').where({ email: data.email }).first();
      if (existing) {
        throw new Error('এই ইমেইল দিয়ে ইতোমধ্যে একাউন্ট খোলা হয়েছে।');
      }

      // ২. আধুনিক Argon2id দিয়ে পাসওয়ার্ড হ্যাশ করা
      const passwordHash = await argon2.hash(data.password, {
        type: argon2.argon2id,
        memoryCost: 65536, // 64 MB
        timeCost: 3,
        parallelism: 4
      });

      // ৩. ইউজার টেবিলে ডাটা ইনসার্ট করা
      const [newUser] = await trx('users')
        .insert({
          full_name: data.fullName,
          email: data.email,
          password_hash: passwordHash,
          status: 'PENDING_VERIFICATION'
        })
        .returning(['id', 'full_name', 'email']);

      // ৪. ক্রিপ্টোগ্রাফিক হাই-এনট্রপি ভেরিফিকেশন টোকেন তৈরি
      const rawToken = crypto.randomBytes(32).toString('hex');
      const tokenHash = crypto.createHash('sha256').update(rawToken).digest('hex');

      // ২৪ ঘণ্টার মেয়াদ নির্ধারণ
      const expiresAt = new Date(Date.now() + 24 * 60 * 60 * 1000);

      // ৫. হ্যাশ সংরক্ষণ
      await trx('email_verification_tokens').insert({
        user_id: newUser.id,
        token_hash: tokenHash,
        expires_at: expiresAt
      });

      // ৬. সিকিউর ভেরিফিকেশন ইউআরএল তৈরি (ইউজারের জন্য)
      const verifyUrl = `${process.env.APP_URL}/api/v1/auth/verify-email?token=${rawToken}&userId=${newUser.id}`;

      // ৭. ব্যাকগ্রাউন্ড কিউ-তে ইমেইল পাঠানোর ইভেন্ট পুশ করা
      await emailQueue.add('SendVerificationEmail', {
        to: newUser.email,
        name: newUser.full_name,
        verifyUrl: verifyUrl
      });

      return {
        success: true,
        message: 'রেজিস্ট্রেশন সফল হয়েছে! দয়া করে আপনার ইমেইল চেক করে একাউন্ট ভেরিফাই করুন।',
        user: { id: newUser.id, email: newUser.email }
      };
    });
  }

  /**
   * ইমেইল ভেরিফিকেশন টোকেন হ্যান্ডলার
   */
  async verifyEmailToken(userId: string, rawToken: string) {
    const tokenHash = crypto.createHash('sha256').update(rawToken).digest('hex');

    const tokenRecord = await db('email_verification_tokens')
      .where({
        user_id: userId,
        token_hash: tokenHash,
        consumed_at: null
      })
      .andWhere('expires_at', '>', new Date())
      .first();

    if (!tokenRecord) {
      throw new Error('ভেরিফিকেশন লিংকটি ভুল অথবা এর মেয়াদ শেষ হয়ে গেছে।');
    }

    await db.transaction(async (trx) => {
      // টোকেন কনজিউম করা
      await trx('email_verification_tokens')
        .where({ id: tokenRecord.id })
        .update({ consumed_at: new Date() });

      // ইউজারকে সক্রিয় করা
      await trx('users')
        .where({ id: userId })
        .update({
          status: 'ACTIVE',
          email_verified_at: new Date()
        });
    });

    return { success: true, message: 'অভিনন্দন! আপনার ইমেইল সফলভাবে ভেরিফাইড হয়েছে।' };
  }
}

১. অটোমেটেড ইন্টিগ্রেশন টেস্ট কেসেস (Jest / Vitest)

import request from 'supertest';
import { app } from '../app';
import { db } from '../config/database';

describe('Auth Registration Integration Tests', () => {
  beforeEach(async () => {
    await db('email_verification_tokens').truncate();
    await db('users').del();
  });

  test('পজিটিভ টেস্ট: বৈধ ৩টি ফিল্ড দিলে সফলভাবে 201 Created হবে', async () => {
    const res = await request(app)
      .post('/api/v1/auth/register')
      .send({
        fullName: 'সাজ্জাদ হোসেন',
        email: 'sazzad@zengfy.com',
        password: 'Password123'
      });

    expect(res.status).toBe(201);
    expect(res.body.success).toBe(true);
    expect(res.body.user.email).toBe('sazzad@zengfy.com');
  });

  test('নেগেটিভ টেস্ট: পূর্বে ব্যবহৃত ইমেইল দিলে 400 এরর দেবে', async () => {
    await request(app).post('/api/v1/auth/register').send({
      fullName: 'ইউজার ১',
      email: 'duplicate@zengfy.com',
      password: 'Password123'
    });

    const res = await request(app).post('/api/v1/auth/register').send({
      fullName: 'ইউজার ২',
      email: 'duplicate@zengfy.com',
      password: 'Password123'
    });

    expect(res.status).toBe(400);
    expect(res.body.message).toContain('ইতোমধ্যে একাউন্ট খোলা হয়েছে');
  });

  test('সিকিউরিটি টেস্ট: ডিসপোজেবল ইমেইল স্বয়ংক্রিয়ভাবে ব্লক করবে', async () => {
    const res = await request(app).post('/api/v1/auth/register').send({
      fullName: 'বোট ইউজার',
      email: 'spammer@10minutemail.com',
      password: 'Password123'
    });

    expect(res.status).toBe(400);
    expect(res.body.message).toContain('ডিসপোজেবল ইমেইল');
  });
});

২. সম্পূর্ণ লোকাল ডকার ডেভেলপমেন্ট পরিবেশ (docker-compose.yml)

version: '3.8'

services:
  # ১. পোস্টগ্রেস ডেটাবেজ
  postgres:
    image: postgres:16-alpine
    container_name: zengfy-postgres
    environment:
      POSTGRES_DB: zengfy_core
      POSTGRES_USER: zengfy_user
      POSTGRES_PASSWORD: secret_password
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data

  # ২. রেডিস (রেট লিমিট ও ক্যাশিং)

৩. ইনসিডেন্ট রেসপন্স ও ট্রাবলশুটিং রানবুক (DevOps SRE Guide)

সমস্যা ১: ইউজারের কাছে ভেরিফিকেশন ইমেইল পৌঁছাচ্ছে না

  1. চেক ১: Redis কিউ-তে কোনো জব জমে আছে কি না দেখুন: redis-cli llen bull:emailQueue:wait
  2. চেক ২: ডোমেইনের SPF ও DKIM ভ্যালিডেশন চেক করুন: dig txt zengfy.top +short
  3. চেক ৩: ইমেইল লগ দেখতে মেলারের কনটেইনার লগ চালান: docker logs zengfy-mailhog

সমস্যা ২: রেজিস্ট্রেশনে বোট অ্যাটাক বা হঠাৎ স্পাইক
